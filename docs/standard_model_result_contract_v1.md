# Standard Model Result Contract v1

## Purpose

Standard Model Result Contract v1 defines the stable model-independent result envelope consumed by Bremen Platform integrations.

Bremen and Aramina may use different scientific pipelines, artifacts, preprocessing, feature engineering, probability names, thresholds, and model-specific outputs. Those differences remain owned by their model packages.

The purpose of this contract is to provide one stable mapped result regardless of which model produced the inference.

Architecture:

Model Package
→ ModelRuntime result
→ Standard Model Result Mapper
→ Standard Model Result v1
→ existing platform/API consumers

This contract is independent from MLflow and any future model packaging technology.

## Compatibility requirement

This contract must be introduced behind the existing Bremen Platform API surface.

Existing endpoints already used by downstream integrations must not be renamed, removed, moved, or changed as part of adopting this contract.

Existing HTTP methods, authentication requirements, job behavior, report behavior, model identifiers, request schemas, and response contracts remain backward-compatible unless explicitly versioned in a separate change.

The initial implementation is an internal mapping boundary.

## Field definitions

### report_id

Unique report identifier generated by the platform. Existing report identifier semantics must be preserved.

### created_at

Timestamp representing creation or generation of the mapped result. The source may correspond to the existing `created_at` or `generated_at` value.

Format: RFC3339-compatible timestamp with timezone and without fractional seconds.

Example: `2026-09-04T19:48:36+02:00`

### analysis_author

Human-readable analysis or bundle author metadata where available. The mapper must not fabricate an author value when no authoritative source exists.

### prediction_comment

Prediction comment exposed by the standard result. This field must also be available for Bremen.

When no prediction comment exists, the implementation may represent it as an empty string according to the schema.

### patient_id

Patient identifier from authoritative source or container metadata. This field must also be mapped for Bremen.

### patient_age

Patient age from authoritative patient metadata. This field must also be mapped for Bremen.

When genuinely unavailable, absence must be represented explicitly rather than fabricated.

### referring_physician

Common patient/source metadata for Bremen and Aramina, immediately after
`patient_age` in serialization; never under `specific_output`. The package-owned
source adapter supplies the normalized field through `SourceMetadata`. Current
supported source contracts provide no authoritative physician value, so it is
exactly `""`. Future packages may supply a real authoritative value. No physician
request field or generic H5 alias is introduced.

### scan_date_time

Timestamp of acquisition, supplied verbatim by the package source adapter and
normalized by the common mapper. A known timezone offset is preserved. A naive
source timestamp stays naive and means **timezone unknown**, not UTC. This is an
explicit ISO8601 exception to the former strict RFC3339 wording; fabricating a
timezone to satisfy that wording is prohibited. See Timestamp normalization.

### operator_id

Operator identifier from authoritative scan or source metadata. This field must also be available for Bremen.

### hardware_version

Hardware version from authoritative acquisition metadata. This field must also be available for Bremen.

### eoscan_version

EOSCAN or acquisition software version from authoritative metadata. This field must also be available for Bremen.

### model_name

Stable model name associated with the selected model package or release. The mapper must use authoritative model identity.

### model_version

Version of the selected model release.

### model_method

Explicit model-method identifier.

For existing models this may currently equal `model_version`, but it remains a separate semantic field and is required for all models.

### model_metrics

Versioned model-level performance metadata.

Contract v1 contains:

- `sensitivity`
- `specificity`

These values belong to model release metadata. They are not calculated from an individual patient inference.

The mapper must not fabricate metrics.

### threshold_value

Threshold used by the authoritative model decision.

The threshold remains model-owned. The mapper must never introduce or hardcode an independent threshold.

### risk_probability

Canonical probability field consumed by downstream integrations.

Model-native probability names are mapped into this field.

Aramina: `p_mri_needed` → `risk_probability`

Bremen: authoritative Bremen risk probability → `risk_probability`

The mapper must not recalculate probability.

### target_class_risk_level

Canonical target-class decision vocabulary.

Contract v1 permits:

- `high`
- `low`

This value must reflect the authoritative model decision.

If mapping requires probability and threshold comparison, it must use model-owned values and reproduce model semantics exactly.

### specific_output

Model-specific extension object.

Model-specific data required downstream but not belonging in the common envelope must be placed here.

## Aramina mapping

Aramina uses the common envelope.

Current model-specific output includes:

```json
{
  "target_side": "left",
  "mammography_suspicious_field": ""
}
```

These fields belong under `specific_output`.

Aramina model-native probability such as `p_mri_needed` maps to `risk_probability`.

Aramina threshold maps to `threshold_value`.

Aramina decision maps to `target_class_risk_level`.

## Bremen mapping

Bremen uses exactly the same common envelope.

Contract v1 requires mapping Bremen metadata including:

- `prediction_comment`
- `patient_id`
- `patient_age`
- `referring_physician`
- `scan_date_time`
- `operator_id`
- `hardware_version`
- `eoscan_version`
- `model_method`

Bremen currently has no required model-specific extension fields:

```json
{
  "specific_output": {}
}
```

The Bremen model runtime remains authoritative for probability, threshold, and decision semantics.

## Timestamp normalization

Both workflows use the same `normalize_timestamp` function at the common mapper
boundary. Inputs must contain a calendar date and a clock time including seconds.
The separator is normalized to `T`, fractional seconds are omitted (truncated,
not rounded), and explicit minute offsets are preserved without UTC conversion.
`Z` becomes `+00:00`; `-00:00` retains its RFC3339 unknown-offset meaning.

Examples:

- `2025-05-28 10:19:55` -> `2025-05-28T10:19:55` (timezone unknown).
- `2025-05-14T12:55:46.123+02:00` -> `2025-05-14T12:55:46+02:00`.
- `2025-05-14T12:55:46Z` -> `2025-05-14T12:55:46+00:00`.

Missing, invalid, date-only, or unsupported timestamp representations produce
`""`; the mapper never invents midnight, an acquisition time, or a timezone.
Platform-generated `created_at` is timezone-aware. Source `scan_date_time` is
RFC3339 when its offset is known, or ISO8601 without an offset when unknown.
Both package adapters currently read their supported acquisition timestamp
verbatim; neither establishes UTC for a naive source value.

## Missing metadata (PR0161)

| Field | Unavailable value |
| --- | --- |
| `referring_physician` | `""` |
| `scan_date_time` | `""` |
| `patient_age` | `null` |
| `eoscan_version` | `null` (not an invented version string) |
| Aramina `specific_output.mammography_suspicious_field` | `""` (unchanged) |

These fields are present, not omitted. Other legacy conventions are unchanged.
`analysis_author` and `prediction_comment` remain caller-provided REST metadata;
they are not inferred from source metadata or model output.

## Failed workflow reports (PR0161)

The existing workflow report endpoint now returns an additive safe failure
envelope for failed Bremen and Aramina runs. The outer `job_id`/`workflow_id`
fields and existing `status: unavailable`, `reason_code: REPORT_NOT_AVAILABLE`
remain. No `payload` or `standard_result` is fabricated for a failed run.

Example (Bremen):

```json
{
  "report": {
    "status": "unavailable",
    "reason_code": "REPORT_NOT_AVAILABLE",
    "failure": "Feature construction failed: raw_peak_gate_failed",
    "failure_stage": "features",
    "failure_reason_code": "raw_peak_gate_failed",
    "failure_detail": "Feature construction failed: raw_peak_gate_failed",
    "remediation": "Review the selected source and model configuration before retrying.",
    "workflow_id": "bremen",
    "model_id": "bremen-paper-reference-v0-2-0",
    "model_version": "0.2.0-paper-reference",
    "patient_id": "SYNTH-1",
    "target_side": "",
    "safe_details": {}
  },
  "job_id": "example-job",
  "workflow_id": "bremen"
}
```

Only exact known public failure strings are preserved. Unknown failures use
`WORKFLOW_EXECUTION_FAILED` with fixed detail/remediation; no exception text is
returned. Explicit normalization failures use `SOURCE_PREPARATION_FAILED`.
Unavailable identifiers/stages use explicit empty metadata where appropriate.
Aramina unsupported-input stage/detail/remediation and preprocessing diagnostics
are regenerated using its existing public allowlists. They appear in the same
`failure_*`, `remediation`, `safe_details` structure as safe job diagnostics.
Unknown diagnostic keys are excluded. No paths, S3 locations, tokens, tracebacks,
checksums, arbitrary package internals, or unallowlisted details are copied.

Job-detail diagnostics are unchanged. A failed sibling workflow does not hide
a completed workflow's report. Unknown jobs/workflows and pending jobs retain
their existing behavior. Successful provider payloads and scientific values
remain unchanged apart from the additive common physician field and documented
timestamp syntax validation.

## Model metrics ownership

Sensitivity and specificity are model-release metadata.

They must be sourced from an authoritative release manifest, artifact contract, model package metadata, or another documented model-release source.

They must not be recalculated per patient or independently duplicated across API modules.

## Mapping responsibilities

The Standard Model Result Mapper may:

- normalize field names
- normalize timestamp representation
- translate model-native probability fields to `risk_probability`
- map the authoritative model decision to `high` or `low`
- assemble platform and source metadata
- assemble release metadata
- construct `specific_output`

The mapper must not:

- preprocess XRD measurements
- generate scientific features
- execute estimators
- inspect model coefficients
- reproduce model-specific scientific formulas
- introduce independent thresholds
- change model probability
- implement separate scientific decision logic
- expose unsafe internal diagnostics

## Safety and privacy

The standard result must not expose:

- local filesystem paths
- S3 credentials
- private artifact locations
- environment secrets
- tokens
- Python tracebacks
- estimator internals
- scaler coefficients
- raw internal exception text
- other non-approved implementation details

## Relationship to ModelRuntime

ModelRuntime remains the callable inference contract.

A model runtime may return a model-native structured result.

Standard Model Result Contract v1 is produced after inference by the mapping layer.

ModelRuntime does not need to know HTTP response schemas.

The mapper does not need to know scientific implementation details.

## Relationship to Model Package Standard v1

Model Package Standard v1 defines ownership of model-specific scientific inference and release metadata.

Standard Model Result Contract v1 defines the stable mapped result consumed by platform integrations.

## Relationship to existing reports

This contract must not break existing report contracts.

Existing report fields including `report.payload.risk_score` and `report.payload.technical_demo_only` must not be moved or removed.

Existing report consumers must remain compatible.

## Relationship to MLflow

MLflow is outside the definition of this contract.

A future MLflow package may transport, load, or register Bremen and Aramina model packages.

MLflow does not define downstream mapping semantics.

## Versioning

The common top-level schema is versioned.

Adding a new model must not require adding model-specific top-level fields.

Model-specific extensions belong under `specific_output`.

Breaking changes require a new contract version and an explicit architecture decision.
