ARAMINA REQUIREMENTS AND PROVIDER INTEGRATION PLAN

STATUS

Planning document.

This document extends the Aramina model requirements manifest plan.

It records the integration gates that must be resolved before Aramina can be safely exposed as a runnable Bremen Platform workflow.

This document does not change runtime behavior.

PURPOSE

Prepare Bremen Platform for Aramina integration while preserving the current safe PR0122 behavior.

PR0122 delivered two production-visible API endpoints:

GET  /demo/api/models/{model_id}/requirements
POST /demo/api/models/{model_id}/requirements/validate

Those endpoints currently return honest no-op / not-available responses.

This document defines how those endpoints should evolve for Aramina once the model package, container contract, and provider wiring are ready.

CURRENT POSITION

Bremen currently has the API surface needed for model requirements discovery and pre-submit validation.

Aramina must not be made runnable just by adding a model artifact.

Aramina requires four gates:

Gate 1: container/data contract
Gate 2: temporary two-sample UI decision
Gate 3: prediction/report decoupling
Gate 4: provider wiring

These gates are sequential in practice.

If the container/data contract is wrong, provider wiring and report work will need to be redone.

CORE RULES

Do not infer container requirements from model.joblib.

Do not hardcode Aramina into the Bremen workflow.

Do not route Aramina jobs to Bremen.

Do not mark Aramina as available until there is a real Aramina provider path.

Do not make clinical, diagnostic, CE, FDA, or regulatory claims.

Do not expose private S3 bucket/key, local filesystem path, raw model package internals, tokens, passwords, or secrets.

REQUIREMENTS SOURCE

Model/container requirements should be read from a separate file located next to the model artifact.

Proposed file:

container_requirements.json

Proposed package layout:

models/<model_id>/
  manifest.json
  model.joblib
  model_description.yaml
  container_requirements.json

Separation of responsibilities:

model.joblib
  Executable model artifact.

model_description.yaml
  Human/model provenance metadata.

container_requirements.json
  Machine-readable input/container contract.

evaluation.yaml and CSV files
  Evaluation/provenance artifacts.

preprocessing config files
  Frozen training/prediction preprocessing inputs.

WHY REQUIREMENTS SHOULD NOT COME FROM JOBLIB

The model artifact can describe what the trained estimator expects after preprocessing.

It cannot fully and safely describe the raw H5/session/container requirements by itself.

Raw input requirements belong to the complete runtime path:

model_id
-> workflow runner
-> preprocessing bridge
-> H5/session container normalization
-> feature preparation
-> feature validation
-> model inference

Therefore container_requirements.json should become the explicit machine-readable source for GET /requirements.

GATE 1 — CONTAINER / DATA CONTRACT

This is the first and most important gate.

Bremen and Aramina need a shared answer to:

What does an Aramina-compatible input container look like?

Known issue to confirm against the container-v0.3 schema:

sample_type appears to be session-level/container-level metadata.

A dual-measurement or dual-breast container may need per-measurement-set side/purpose metadata.

If a container can hold measurements from both sides, a single session-level sample_type is not enough to identify each measurement set.

Recommended direction:

Add or confirm a per-measurement-set field that records side/purpose for each measurement set.

Examples of possible semantics:

target_breast
contralateral_breast
left
right
unknown

The exact field name must be agreed with the container owner.

Session-level sample_type can remain as a coarse label, but it should not be the source of truth for per-set side/purpose in multi-sample containers.

Bremen should not invent this contract alone.

The next concrete cross-team deliverable is a literal container-v0.3-shaped example configuration showing how the dual-sample Aramina case should be represented.

GATE 1 OUTPUT

Required before runnable Aramina integration:

1. Agreed per-measurement-set side/purpose representation.
2. Example container-v0.3-shaped configuration.
3. container_requirements.json draft for Aramina.
4. Agreement on which metadata is required vs optional.
5. Agreement on how age availability is represented.
6. Agreement on how target and contralateral measurement counts are represented.
7. Agreement on how symmetry availability is derived.

GATE 2 — TEMPORARY TWO-SAMPLE UI DECISION

A temporary UI simplification may be acceptable:

Ask for two samples universally, even if Aramina may only need one clinician-selected target sample.

This must be recorded as temporary technical debt, not a permanent design.

Temporary rule:

UI currently requests two samples universally.

Known Aramina requirement may be narrower:

Aramina may only require one clinician-selected target sample, with optional contralateral/symmetry refinement depending on available measurements.

Do not bake the universal two-sample assumption too deeply into:

- report logic;
- validation logic;
- model requirements contracts;
- UI state model;
- workflow routing.

This decision should be revisited after Bremen and Aramina both run through real demo workflows.

GATE 2 OUTPUT

1. Named technical debt item for universal two-sample UI.
2. Clear statement that Aramina target-sample flow may diverge.
3. No report implementation that assumes two samples permanently.
4. No container validation contract that falsely requires two samples unless Aramina requirements file explicitly says so.

GATE 3 — PREDICTION / REPORT DECOUPLING

Report generation should not be tightly coupled to raw prediction implementation details.

Bremen has already had field-name mismatch problems between prediction output and report rendering.

The safe rule:

Use a shared minimal prediction-result shape underneath model-specific report rendering.

Reports may be hardcoded per model type for demo purposes.

But the underlying prediction-result data contract should be stable and shared.

Recommended minimal prediction-result shape:

{
  "schema_version": "bremen.prediction_result.v1",
  "technical_demo_only": true,
  "job_id": "...",
  "model_id": "...",
  "workflow_id": "...",
  "model_version": "...",
  "timestamp": "...",
  "score": 0.0,
  "threshold": 0.0,
  "decision_code": "...",
  "recommendation": "...",
  "quality": {
    "status": "passed"
  },
  "details": {}
}

Model-specific report templates may render this differently.

Bremen report can render MRI continuation decision-support.

Aramina report can render tissue-risk assessment / target-breast risk decision-support.

The shared shape prevents report templates from depending on incompatible internal field names.

GATE 3 OUTPUT

1. Minimal shared prediction-result contract.
2. Bremen adapter maps current Bremen result into that shape.
3. Aramina adapter maps Aramina result into that shape.
4. Report rendering remains model-specific.
5. Report endpoint does not become the input validation layer.

REPORT ENDPOINT ROLE

The report endpoint is downstream.

It should validate:

- auth;
- job_id exists;
- report exists;
- report provider exists;
- output can be safely serialized.

It should not validate raw H5/container requirements.

Input/container validation belongs before job creation:

GET  /demo/api/models/{model_id}/requirements
POST /demo/api/models/{model_id}/requirements/validate
POST /demo/api/jobs
GET  /demo/api/jobs/{job_id}/reports/{workflow_id}

GATE 4 — PROVIDER WIRING

Only after Gates 1-3 have enough of an answer should Bremen wire Aramina as a runnable provider.

Current rule:

Do not open workflow_id=aramina as executable catalog support until a real provider exists.

Before provider exists, Aramina can only be display-only/unavailable if explicitly implemented that way.

Required behavior for unavailable Aramina catalog entry:

technical_ready=false
scientifically_certified=false
technical_demo_only=true
availability=unavailable
workflow_id=aramina

Provider integration options to confirm:

Option A: in-process provider call.
Option B: subprocess isolation.
Option C: separate HTTP/service call.

The selected option determines whether the earlier subprocess-isolation governance still applies or needs an updated ADR.

GATE 4 OUTPUT

1. Confirm provider execution mode.
2. Add explicit workflow_id=aramina support only when there is a safe backing provider.
3. Add clean WORKFLOW_NOT_IMPLEMENTED behavior if catalog support appears before full execution.
4. Add Aramina runner adapter.
5. Add Aramina result adapter to shared prediction-result shape.
6. Add Aramina report provider/template.
7. Add Aramina E2E smoke data and tests.

Do not implement real validation yet.

Do not open H5 in validate yet.

Do not run inference in validate.

Do not create jobs in validate.

Do not create reports in validate.

HOW PR0122 ENDPOINTS EVOLVE

Current PR0122 behavior:

GET /requirements returns:

requirements_available=false
status=requirements_not_declared
required_container_contract=null
required_fields=[]
optional_fields=[]

POST /requirements/validate returns:

validation_available=false
validation.status=not_available
validation.ready_to_run=null
validation.requirements_checked=false
validation.inference_job_created=false
validation.report_created=false

Future manifest-backed behavior:

GET /requirements should read container_requirements.json and return:

requirements_available=true
status=requirements_declared
required_container_contract=<manifest value>
required_fields=<manifest value>
optional_fields=<manifest value>

POST /requirements/validate should use the selected model's container_requirements.json and the selected input container to return:

validation_available=true
validation.status=passed | failed
validation.ready_to_run=true | false
validation.requirements_checked=true
validation.inference_job_created=false
validation.report_created=false
missing_required_fields=[]
invalid_fields=[]

The validate endpoint must remain pre-submit.

It must not create an inference job.

It must not create a report.

ACCEPTANCE CRITERIA FOR THIS PLAN

This plan is complete when it records:

1. Requirements come from container_requirements.json next to the model.
2. Aramina requires a container/data contract gate before provider wiring.
3. Universal two-sample UI is temporary technical debt.
4. Prediction/result data shape should be decoupled from report rendering.
5. Report endpoint is not the input validation layer.
6. workflow_id=aramina must not be enabled as executable until provider exists.
7. Aramina must not be routed through Bremen accidentally.
8. No runtime behavior changes are introduced by this document.
9. No clinical/regulatory claims are added.
